# gpt-oss-120b on trn1.32xlarge (2026-10-03)

Instance trn1.32xlarge `kiln-mimo-trn1` (us-east-2c spot), Neuron SDK 2.32 DLAMI (neuronx-cc
2.27.5334.0, libtorch-neuronx-lite 2.11.0.1.0.1284, vllm-neuron 0.24.0.1.1.0 in the same venv),
model `openai/gpt-oss-120b` revision `b5c939de8f754692c1647ca79fbf85e8c1e70f8a` (117B / 5.1B
active, 36 layers alternating sliding-window 128 / full attention with sinks, 128 experts top-4,
MXFP4 experts, BF16 elsewhere; 61 GiB of `model-*.safetensors`). bf16 activations and KV,
vocab-parallel embedding and lm_head, `--piecewise` (every MoE layer its own graph; gpt-oss is MoE
in all 36 layers), XLA expert path (the NKI MoE kernel does not compute gpt-oss's expert biases or
clamped GLU, so `KILN_MOE_KERNEL=nki` refuses this model). Experts are MXFP4 converted losslessly
to FP8 with bf16 power-of-two block-32 scales unless `--mxfp4-packed`. All commands run from the
repo root through `infra/fleet.sh py kiln-mimo-trn1 ...` with `KILN_BOX_SRC=/opt/kiln/src-gqa`;
`MODEL` is the snapshot directory `/opt/kiln/hf/hub/models--openai--gpt-oss-120b/snapshots/b5c939de8f754692c1647ca79fbf85e8c1e70f8a`.

## Decode speed

`python tools/check_device.py --model MODEL --tp T --piecewise --bench-only --bench-batches 1,4,16
--tokens 32 --bench-steps 32 --prefill-tokens 32 --max-model-len 1024 --kv-cache-gb 1`, step p50 over
32 steps (p90 in brackets), 4-page context (P=4):

| config | B=1 | B=4 | B=16 |
|---|---|---|---|
| tp=32, FP8 experts, run 1 (a host-only job was loading on the CPUs) | 198.0 ms (235.6) | 223.9 ms (291.6) | 176.0 ms (250.7) |
| tp=32, FP8 experts, run 2 (with `--host-reference`) | 210.4 ms (234.4) | 229.9 ms (241.6) | 129.8 ms (222.8) |
| tp=16, FP8 experts, `KILN_MOE_GATHER_MAX_PAIRS=64` | 155.1 ms (159.4) | 154.6 ms (158.0) | 1505.4 ms (1506.6) |
| tp=8, packed MXFP4 experts (`--mxfp4-packed`), `KILN_MOE_GATHER_MAX_PAIRS=64` | 844.7 ms (858.5) | 1831.4 ms (1840.6) | 37568 ms (37583) |

tp=32 is 5.0-5.1 tok/s at B=1, 17-18 at B=4 and 91-123 at B=16. The step is about 36 graph
executions of one MoE layer each plus prep and post, and docs/neuron-notes.md measures any graph with
a cross-chip collective at about 5 ms (32 ranks) and 3.8 ms (16 ranks) per execution, which is most of
these steps. At tp=16, B=16 (64 gathered (token, expert) pairs of 192-unit expert shards per layer)
is 10x slower than B=4; this is the expert-gather packetization the NKI kernel addresses, not tuned
here. tp=16 needs `KILN_MOE_GATHER_MAX_PAIRS=64` (prefill on the every-expert path): its C=32 gather
prefill graph compiled for 27 minutes and then could not be loaded (descriptor limit, notes).

tp=8 needs the packed MXFP4 experts (not tried with FP8, computed from the shapes): FP8 experts
would be 15.3 GB per rank (36 layers x 128 experts x 3 x 384 x 2880 bytes) plus 1.0 GB of scales
against a NeuronCore's 16 GiB (17.2 GB) before attention, embeddings, KV and NEFF reservations; packed
they are 8.6 GB. tp=8 is slower than tp=32 although its collectives are cheaper (2.45 ms per graph at
8 ranks, notes); the likely cost is the in-graph 4-bit decode of every gathered expert (vector-engine
work, models/quant.py), not profiled here. The tp=8 packed engine is the closer of the two
configurations checked against the host (`--host-reference`, same reference file):
4/8 prompts token-exact over 32 tokens (Paris 32/32, Trainium 24, sky 12 at a top-2 gap of 0.009,
Apollo 7, fibonacci 0), teacher-forced max |dlogprob| 0.057-0.104 and the host's token ranked first
at every one of the 256 positions; compiles took decode (8, 4) 514 s and prefill (32, 4) 712 s.

Engine start with a warm page cache: weights 41.7-54.5 s at tp=32, 225.2 s at tp=16; compiles at
tp=32: decode (1, 4) 22.2 s, (4, 4) 25.4 s, (8, 4) 29.5 s, (16, 4) 34.9 s, prefill (32, 4) 45.6 s.

## vllm-neuron 0.24 on the same instance: does not run gpt-oss on trn1

The SDK's own gpt-oss recipe (`docs/model-recipes/gpt-oss.md` in the DLAMI's
`/vllm/aws_neuronx_venv_pytorch_inference_vllm_0_24_0_1_1_0/`, dated 2026-07-15) lists Trn2 (BF16)
and Trn3 (MXFP4) only. To check trn1 directly instead of assuming, I ran
`python bench/vllm_neuron_decode.py --model <gpt-oss-20b snapshot 6cee5e81ee83917806bbde320786a8fb61efebee> --tp 8 --batch 4 --tokens 32`
(with `KILN_BOX_SRC=/opt/kiln/src-gqa`, 2026-10-03 19:43 UTC). It launches the model the way the
recipe's `vllm serve` does: `hf_overrides={"quantization_config": {}}` and the hybrid KV cache
manager on. Without the override, vLLM refuses the checkpoint ("gpt_oss_mxfp4 quantization is
currently not supported in neuron"). The run also sets `NEURON_SKIP_EFA_AFFINITY=1` (the worker's
EFA table has no trn1 row) and turns prefix caching off (vllm-neuron refuses it with single-shot
prefill).

The model then loads onto vllm-neuron's BF16 implementation, `model_bf16.py`, which the factory picks
on every platform that is not trn3. It fails while tracing its first decode graph, in the NKI
attention-mask kernel (`functional/attention/attention_decode_mask.py`, `_gen_mask_via_kernel`):

```
error: failed to compile NKI kernel: assertion failed: tensor_copy does not support engine.scalar on
NeuronCore-v2 (Trn1/Inf2). Use nisa.activation with op=nl.copy instead.
```

This is a NeuronCore-v2 restriction inside a shipped kernel, and gpt-oss-120b's BF16 model calls the
same kernel. So there is no vllm-neuron number to compare against on trn1, and the Kiln figures above
have no managed-stack baseline on this instance type.
